title: "Networking"
description: "How sandboxes connect to the host and the internet, and what they can't reach."

Each sandbox gets its own network namespace. Sandboxes can reach the internet through NAT on the host, but cannot reach the host's services or private and link-local networks. Traffic between VMs is blocked unless their tenant opts in.

## The network stack

```text
Internet
    |
  Host eth0 (NAT via nftables)
    |
  br-flint bridge (10.0.0.1/24)       each sandbox port is isolated
    |
  ┌──────────────────────────────────┐
  │ Network namespace: fc-{id}       │
  │                                  │
  │  veth (10.0.0.X)  ← ingress firewall, egress policy
  │        │                         │
  │  TAP device (172.16.0.1)         │
  │        │                         │
  │  VM eth0 (172.16.0.2)            │
  │  guest agent on 172.16.0.2:5000  │
  └──────────────────────────────────┘
```

A few things worth explaining here:

- **`br-flint`** is a Linux bridge on the host. Think of it as a virtual switch. All sandbox network namespaces connect to it.
- Each sandbox gets a **veth pair** - one end inside its network namespace, one end attached to the bridge.
- Inside the namespace there's a **TAP device** that the VM uses for its network interface.
- The VM's guest IP is `172.16.0.2`. The host-side address inside the namespace is `172.16.0.1`.
- Each namespace gets a unique address in `10.0.0.0/24` for its outbound traffic. No two live namespaces ever share one, including across daemon restarts. Storage exports are authorized by this address. The subnet caps a host at 253 namespaces with internet access, pre-built ones included.

## Isolation

The attacker Flint defends against is the code inside a sandbox. Every boundary below is enforced in two places, so one misconfigured layer doesn't open it.

| A sandbox can't reach | Enforced by |
|---|---|
| Other sandboxes' namespaces | Bridge port isolation (`isolated on`) + each namespace drops unsolicited traffic arriving on its veth |
| Services on the host (any address) | Host nftables input chain + namespace egress policy |
| Private, loopback, CGNAT, multicast and link-local destinations, including cloud metadata at `169.254.169.254` | Namespace nftables egress chain + host forward chain |
| Another sandbox's credential proxy | The proxy listens only on `172.16.0.1` + the namespace ingress firewall |

The only exception to the egress policy is the workspace storage server, when one is configured: `r2nfs` on the bridge IP, or the S3 Files NFS endpoint. IPv6 is disabled inside sandbox namespaces.

Flint also explicitly allows sandbox traffic out through the host's `FORWARD` chain. Docker sets the host's forward policy to `DROP`, which would otherwise cut sandboxes off from the internet.

## Same-tenant traffic

A service token can opt its tenant into peer networking on a single Linux host:

```bash
curl -X PUT http://localhost:9100/v1/tenants/customer-a/network \
  -H "Authorization: Bearer $FLINT_API_KEY" \
  -H 'Content-Type: application/json' \
  -d '{"allow_same_tenant": true}'
```

The response is `{"tenant":"customer-a","allow_same_tenant":true}`. Read it with `GET /v1/tenants/customer-a/network`. A token cannot change another tenant's network (`403`); invalid bodies return `400`. Clusters and the macOS backend reject changes with `409`.

Connect to another VM using its `network_address` from `GET /vms/{id}`, preserving your application's port. Both VMs must belong to the same opted-in tenant and have a bridge uplink (`allow_internet_access=True`). Guest IPs remain private to their namespaces.

Bridge ports stay isolated. Routes send peer traffic through the host, which checks the source and destination pair; the destination namespace forwards only approved peers to guest services. TCP ports `5000` (guest agent) and `8080` (credential proxy, or your configured proxy port) stay blocked. Setting `allow_same_tenant` to `false` revokes the host ACL for new and established connections. Settings persist across daemon restarts and apply to newly created and resumed VMs.

## Resource ceilings

Both Linux backends require native `nftables`, `tc` from `iproute2`, and cgroup v2 with the CPU, memory, IO and PID controllers. Firecracker root disks require a local block-backed filesystem for `io.max`. Cloud Hypervisor also configures its virtio-block limiter, including for shared NFS/CEPH root disks. Fresh and recovered processes must belong to their configured cgroup before they are served; recovery rejects a shared-disk VM whose disk limiter cannot be verified. Startup fails if these boundaries cannot be configured.

Each VMM gets CPU and memory ceilings, a 512-task ceiling, and a root-disk IO limit. The guest's TAP shapes inbound traffic and polices outbound traffic, including storage traffic. Host settings apply to every VM:

| Environment variable | Default | Unit |
| --- | --- | --- |
| `FLINT_DISK_BYTES_PER_SECOND` | `104857600` | Bytes per second through the root-disk limiter (Cloud Hypervisor also limits shared disks) |
| `FLINT_NETWORK_BYTES_PER_SECOND` | `12500000` | Bytes per second in each network direction |

Values must be positive integers. These limits complement tenant quotas; shared storage is also bounded by the VM's network ceiling.

## Pre-built namespaces

Building a namespace (TAP, veth, firewall) takes about 40 ms, so the daemon keeps a pool ready: 8 with internet access (`FLINT_NETNS_POOL_SIZE`) and 2 without. A pre-built namespace:

- gets the same rules as one built on demand before any VM uses it, so an idle namespace on the bridge is unreachable;
- belongs to exactly one sandbox and is deleted with it, never reused;
- has nothing sandbox-specific (credential proxy, network policy) applied until a sandbox claims it.

Unclaimed namespaces are deleted when the daemon stops, or at the next start after a crash.

## How the daemon reaches flintd

When the daemon needs to call `flintd` (to run a command, read a file, etc.), it enters the sandbox's network namespace using `nsenter` or `ip netns exec`. From inside the namespace it can reach the VM at `172.16.0.2:5000`.

This is why the guest agent is not directly accessible from outside the Flint daemon - it's only reachable from within the network namespace.

## Internet access

If `allow_internet_access=True` (the default), the VM's traffic is NATed out through its veth and then through the host's default route.

If you set `allow_internet_access=False`, the namespace has no veth: the VM can reach nothing outside it.

## Implementation

Networking is set up in `src/flint/core/net/netns.py`, and the pool lives in `src/flint/core/net/netns_pool.py`. By default Flint uses [pyroute2](https://pyroute2.org/) to create and configure the namespace, but you can fall back to shell commands with `use_pyroute2=False` if pyroute2 isn't available. Both paths apply the same isolation rules.
